Big Red Routes

A Raspberry Pi–based physical TCAT bus tracker that uses live transit data to illuminate a 3D-printed map of Cornell and Ithaca routes.

GitHub Demo video Project report

Selena Zhang and Helen Ni · May 9, 2026

Overview

Interactive transit information.

Big Red Routes is an interactive TCAT (Tompkins Consolidated Area Transit) bus tracker for the Cornell and Ithaca community. It turns bus location data for Routes 30, 81, and 92 into an interactive, 3D-printed map rather than a conventional screen-only map. The initial concept was inspired by a Manhattan subway-map project.

At startup, active buses on all three routes are displayed. Users can either select one route to track or choose a start and end stop for a direction-aware trip path. The project was completed as the final project for Cornell’s ECE 5725 course, which focuses on embedded Linux systems and target-device debugging.

Hardware

3D-printed map, fiber optics, and a Raspberry Pi display stack.

The 12 × 21 inch Ithaca map was hand-traced in Figma using vectors, exported as SVG, and imported into Fusion for extrusion, color, and 3D printing. It was printed as six puzzle-like pieces and elevated by eight printed pillars, leaving room below for the LED matrix, fiber-optic cables, and electrical wiring.

The hardware consists of a Raspberry Pi 4, a 16 × 32 Adafruit RGB LED matrix, a PiTFT 2.8 inch display, four external buttons, and a speaker. The Pi and PiTFT are mounted on one corner of the map. Green light denotes outbound travel (north to south); red light denotes inbound travel (south to north).

Physical display design

The LED matrix was a simpler and cleaner alternative to using tens of individual LEDs. Each of the 89 stops uses a 1 mm fiber-optic cable to carry a matrix pixel’s light to a hole in the map. A 5 mm tall printed board with 1 mm holes holds the fiber ends over the matrix.

External, color-capped buttons were added because the matrix uses GPIO pins that conflict with the Raspberry Pi’s built-in buttons. The speaker announces the bus number, direction, and stop name when a bus moves to a new stop on the route being viewed.

Software

Focused modules for data, I/O, display, and route selection.

The project documentation records Raspberry Pi OS kernel 6.1.21-v8+ #1642 SMP PREEMPT on the target system.

tcat_api.py
Downloads and parses TCAT GTFS static files (stops.txt, trips.txt, and stop_times.txt), fetches the live vehicle feed, normalizes direction labels, and builds displayable bus snapshots.
route_data.py
Stores stop IDs, names, matrix coordinates, directional stop order, picker order, and permitted transfer points for Routes 30, 81, and 92.
bus_tracker.py
Runs the 10-second poll loop, updates GUI state, redraws the selected route, uses Route 92 replay data when needed, and triggers arrival announcements.
led_matrix.py
Wraps rgbmatrix with the Adafruit HAT mapping, PWM and brightness configuration, a lock-protected active-pixel map, and SwapOnVSync redraws.
gpio_buttons.py and gui.py
Handle stateful button navigation and Pygame PiTFT rendering for the home screen, route selection, trip finder, stop picker, trip summary, and live bus details.
find_a_route.py and audio_announcer.py
Search a direction-aware transit graph and light the resulting route; queue one-at-a-time espeak announcements in a background worker.

Features

Two physical interaction modes and live status details.

  • Track a Route. The green, blue, and red buttons select Routes 30, 81, and 92; the selected route’s active buses are displayed on the map and the PiTFT can cycle through bus details. Route 30 is shown in green on the PiTFT, Route 81 in blue, and Route 92 in red.
  • Find a Route. Users select an inbound or outbound direction, a starting stop, and an end stop. The resulting path prioritizes fewer transfers, then fewer ride steps and total path length.
  • Physical route feedback. The matrix highlights bus locations, selected stops, and planned route segments. The PiTFT shows status, last stop, destination, direction, and occupancy. The white button selects or returns home; green and blue move through stops, with scrolling accelerating when held.
  • Audio arrivals. When a bus changes stops on the selected route, the speaker announces the route number, bus ID, stop name, and direction.

Challenges and engineering decisions

Integration choices made on the target system.

  1. Input remains responsive while data and audio run.

    bus_poll_loop(), gpio_button_loop(), the PiTFT loop, and AudioAnnouncer have separate responsibilities. GPIO sends commands through screen and LED queues; the matrix uses a lock, and audio uses its own queue and thread so speech does not freeze the rest of the system.

  2. The PiTFT and LED matrix work within GPIO constraints.

    PiTFT code from a previous Lab 3 exercise was integrated with the matrix. The touchscreen was not responsive enough for the intended interaction, so physical GPIO buttons became the primary control path. Because the matrix conflicts with the Pi’s built-in button pins, four external buttons were wired to free GPIO pins.

  3. Static and live transit data are joined.

    The application loads static GTFS metadata at startup and polls the GTFS-Realtime vehicle feed every 10 seconds. Route-specific direction normalization handles differing headsigns. Route 92 does not always have live data during the day, so recorded snapshots are replayed when the selected live feed is empty.

  4. Direction and transfers are modeled explicitly.

    Testing many start/end combinations showed that inbound and outbound stop data needed to be separate so users could not select a backward path. Additional stop and transfer dictionaries were added to correct missing directional cases and constrain valid transfers.

  5. The hardware and integrated system are tested.

    Printed test pieces compared fiber-hole sizes in Figma and Fusion. Independent matrix test code isolated blinking and flashing to the matrix hardware rather than application code, leading to a replacement panel. Print statements checked transit records, buttons, PiTFT updates, threads, and audio before the Pi, display, matrix, buttons, polling, and speaker were tested together. The team also tested power-up through a .bashrc invocation of main.py and Raspberry Pi Console Autologin.

Results and future work

Integrated system result

The final system displayed real-time TCAT information on the 3D-printed map for the selected routes. It added GPIO controls, Find a Route, and audio announcements to the original tracking concept. The main change during development was the selected routes; the project’s physical transit-display purpose remained the same. Separating the GUI, LED matrix, bus tracking, buttons, audio, and route data into different files made the integrated system easier to manage.

With additional time, the project could add more TCAT routes and labels for major Cornell locations, use classes rather than lists of dictionaries for bus data, and connect trip planning to live arrival times, nearby buses, and walking vs waiting information. The PiTFT menus could use fewer words and more icons, and the audio voice could be made smoother and more natural.
